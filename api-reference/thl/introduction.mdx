THL (Tourism Holdings Ltd) rents campervans and motorhomes across five AU/NZ brands — **Maui, Britz, Mighty, Apollo, MightyLITE** — plus separate US and Canada brands. Its agent/reseller integration is **"Aurora OTA"**: an [OpenTravel (OTA)](https://opentravel.org) vehicle-rental message set delivered over **SOAP**.

<Note>
**This section is scoping, not yet confirmed live.** Everything here is sourced from THL's *OTA Technical Documentation* (13 Aug 2026) and its appendices, **before** we have called the API. Mark each finding **confirmed live** (and roughly when) once a real staging call proves it; until then treat it as "documented, unverified". Codes and product IDs are examples — look yours up again.
</Note>

## How it differs from our other transport suppliers

This matters because it sets the build cost. Neither thing below exists in the TransportSOA Worker today.

| | THL Aurora OTA | Jucy | RCM |
|---|---|---|---|
| Transport | **SOAP 1.1 / 1.2 (XML)** | REST / JSON | REST / JSON |
| Auth | **Static API key header (`x-api-key`)** | static API key | HMAC signature per call |
| Product content | **IDs only** (content is a static list) | rich content via API | IDs only |
| Rate | **Net** (we add margin) | — | — |

So the real work in a THL build is just a **SOAP/XML client** — the booking flow itself maps cleanly onto our contract (see [Booking flow](/api-reference/thl/booking-flow)), and as of Nov 2026 auth is a static header, not a session. An earlier revision used a `LoginOK` session with a JWT replayed as `EchoToken`; THL has since **replaced that with the `x-api-key` header** (Guide D), removing the token-cache / re-login work entirely. The SOAP transport is the only net-new cost left.

Ignore the `.asmx` path.
</Note>

<Note>
**Staging auth error shapes, confirmed live (2026-11-08)** — the gateway is AWS API Gateway, so errors are JSON, not SOAP faults:
- **No `x-api-key`** → `401 {"message":"Unauthorized"}`.
- **Invalid `x-api-key`** → `403 {"Message":"User is not authorized to access this resource with an explicit deny in an identity-based policy"}`.

So a **403 with that capital-`Message` body means the key was sent but rejected** (same as a bogus key) — a bad/not-provisioned key, *not* a wrong endpoint. The key is issued/managed in **Motek B2B**.

**"One key works both hosts" (Guide D) is confirmed FALSE (2026-11-08).** Our first-issued key **authenticates against production** (`https://api.thlonline.com/xml` returned a real `OTA_VehAvailRateRS`) but is **rejected on staging** (`api-staging…/xml` → the bogus-key 403). So a key is **host-scoped** — a staging key must be enabled for the staging host specifically. Plan for a **separate key per host**, and don't assume a prod key unlocks the sandbox.
</Note>

The underlying rental platform is **"Motek"** — branch/location codes in requests are Motek codes (see Appendix B). The B2B admin that issues the API key is **Motek B2B** (`https://b2bmotek.thlonline.com`; older portal `https://motek.b2b.thlonline.com`).

## Authentication — a static API key header

THL **replaced the login/token session** with a static API key (Guide D, Nov 2026). Current model:

1. A B2B admin generates an API key in **Motek B2B** (Settings → Accounts → API Key → *Generate*). It is shown once then hidden; lost keys are regenerated, and a key can be revoked.
2. Send it as the **`x-api-key`** request header on **every** OTA call. No login call, no token in the payload.
3. Keys stay valid **until revoked or replaced** — no expiry, no refresh.

Implications for a Worker build (all simpler than the old session):
- **No token cache, no re-login, no `LoginOK` call.** Auth is now as simple as Jucy's static key — just a header.
- The old `EchoToken` in the request body is **gone** — remove it from every payload.
- Keep the API key as a **per-Worker secret** (set out of band with `wrangler secret put`, the same as `JUCY_API_KEY` and the RCM keys — read synchronously as `env.THL_API_KEY`, *not* an account Secrets Store binding), never in a repo or these docs.

<Note>
The earlier session model (`LoginOK` → JWT → `EchoToken`) is **deprecated**. The "NEW API Technical Documentation" still contains stale per-call cURL examples using the old `otautils` host and an EchoToken — ignore those; Guide D and the sample cURL are the current word on auth.
</Note>

## Common request parameters

Auth is the `x-api-key` **header** (above). The rest ride in the SOAP body:

| Parameter | Meaning |
|---|---|
| `Target` | `Production` for live, `Test` for test. Advisory only — identifies request origin. |
| `Version` | Message version (e.g. `1`). |
| `MaxResponses` | Cap on results returned (e.g. `3`). |
| `TimeStamp` | When the request was sent. |
| `POS` / `Source` | Point of sale: `RequestorID` `Type` = `22` (default), `ID` = agent code. |
| `ISOCountry` | e.g. `AU`. If omitted, OTA returns defaults (VehAvailRate defaults to `GP`). Passing it null/empty throws an error. |

**Headers:** `UserAgent`, `Content-Type` (`text/xml`) and **`x-api-key`** are mandatory; `SOAPAction` is optional (but SOAP 1.1 typically wants it, e.g. `http://www.thlrentals.com/Aurora/OTA/VehAvailRate`).

## Rates — net by default, gross (RRP) on request

THL's AU/NZ brands are **net rate** by default — *"All ATL brands are net rate"* — so TransportSOA applies the margin, consistent with the WebsiteTravel model. The rate type is a **mandatory `Status`** request parameter, and you get **one or the other per call**, never both at once:

| `Status` | Vehicle rate returned |
|---|---|
| `Available` | **Net** (what we mark up) |
| `Gross` | **Gross** — the RRP |

The response's `RateCategory` confirms which came back (`1` = Gross, `0` = Net). To show both net *and* RRP you'd make two calls, or take net and add the margin.

<Warning>
**Live finding (2026-11-23, staging) — `Status=Gross` alone returns NO availability.** A real AKL search that returns 30 vehicles at net (`Status=Available`) returns *"no availability"* at `Status=Gross`, for all brands and per single brand (Maui, Britz tested). The net rates come back under `PromotionCode`s all suffixed **`N`** (`MIGHTYN`, `BRITZN`, `APOLLON`, `MAUIN`, `MIGHTYNL`), which suggests **gross is selected by a different `PromotionCode`/`RateQualifier` (the non-`N` brand code), not by `Status` alone** — our request sent an empty `RateQualifier`. UNRESOLVED: either these brands are net-only, or the gross request is under-specified. **Confirm with THL** what request yields the Gross/RRP before relying on a two-call RRP (and before building any gross-vs-net margin monitor). The CMS-margin pricing path does not depend on this.
</Warning>

**Extras and insurance are different** — `GetExtraHireItems` returns **both** `GrossAmt` and `NettAmt` on every product, side by side (in THL's samples they're equal, but the fields carry both).

<Note>
This is a different pricing model from our other two suppliers. **Jucy and RCM are a commission model** — they return a gross/retail rate **plus an `agentCommission`**, and net is derived (gross − commission). **THL returns net directly** and has no commission concept; gross is just the alternate `Status`.
</Note>

### Feeding TDMS, which expects gross

TDMS expects TransportSOA to send a **gross** sell price (with commission), exactly as Jucy and RCM already do. THL gives us net and **no bridge** to gross — one response never yields the other, and there is no commission field — so for THL we have to *produce* the gross. Two ways:

- **Default: apply a WebsiteTravel margin to net** (one `Status=Available` call). `gross = net + margin`, and the commission we report **is** that margin. This fits the existing "net rate, we add the margin" model — but the margin is a **new THL config input**, because Jucy's/RCM's commission is supplier-set and varies by key, whereas THL's is ours to define.
- **Alternative: honour THL's own RRP** (two calls — `Available` + `Gross`). Send THL's `Status=Gross` as the gross and set `commission = gross − net`. Only worth it if TDMS must show THL's published retail; costs a second call and reconciling two responses.

Either way TDMS receives gross + commission. The real difference from Jucy/RCM: **their commission is the operator's** (per-key), **THL's is ours to define** — so a THL build needs a margin rule that the other two suppliers never required.

**The commission is a % of RRP, set by the operator** — that's the WebsiteTravel model for every supplier: the agent earns that %, and `net-to-operator = RRP − commission`. Jucy/RCM hand us that commission in the response; THL doesn't, so we reconstruct the % from CMS (next).

**Settlement stays correct even if a margin ever disagreed.** We **record THL's actual net as what we owe the operator**, carried straight through — not back-computed from gross. So if a stored margin ever differed from THL's real commercial margin, the operator is still paid their exact net (no accounting headache); a mismatch could only change the *displayed sell price*, never the settlement. By convention the CMS margin equals THL's margin anyway, so single-sourcing it from CMS (next) keeps the sell price right too.

Other things the real payloads confirm — these are **endpoint-shape** facts. The sample captures were **non-THL products shown for shape only**, so treat the field *shapes* as authoritative, not the specific fares or numbers:

- **Amounts are strings** — `"rrp": "695.00"`, `"netRate": "451.75"` — parse them, don't assume numbers (the same stringify-numbers habit TDMS has everywhere).
- **`agentPricingGroupId` can be `null` *or* a real group id** (e.g. `6471`, `6813`). The `null` rows are the **default pricing group**, and that's the one **our build consumes**. The same fare, same RRP, can appear under several groups at different nets — the shape that makes *Pricing tiers* (below) possible. Whether a given THL product actually uses non-null groups is a CMS-config question these samples don't settle.
- **Select by group *first*, then default.** Pick `status = "Live"` **and** `agentPricingGroupId = <our group>` (null) **and** `defaultFare: true`, within the live `periodStart/End` + `travelStart/End` window. A product can carry many Live rows (other groups, Child, add-ons, open-dated), so `defaultFare` alone is ambiguous.
- **`netRate` can be `"0.00"` on a Live fare** — the zero-net guard isn't theoretical; an undefined ratio must be flagged/skipped, never divided.
- **Dates can be open** — `periodEnd`/`travelEnd` may be `null` (open-dated); don't assume bounded windows.
- **`bookingSystemMapping`** (present on some rows) links the fare to the booking-system product and the **supplier login** — `"bookingSystemName": "Generic"`, a `supplierLogin`, plus a booking-system `productId`. Relevant to anchoring the booking alongside the PPDID.

These records are **placeholders**: for a supplier-API product like THL the CMS product/price carries only two things that matter — the **margin** (which can differ per product) and a **PPDID** (`productPricesDetailsId`, e.g. `7001`) that the **booking is held against** in CMS. So from this call capture **both** per product, cached together: the margin for pricing, the PPDID to anchor the booking.

The stored amounts are **indicative — what matters is the margin they imply** (e.g. `rrp 100 / net 75` → a **25% margin**). Take the **`Live` default** fare for our pricing group, in THL's currency, and apply that margin to **THL's live net** using the ratio:

```
ratio       = rrp / netRate          # 100/75 = 1.333  (25% margin on RRP == 33% markup on net)
gross       = thlNet × ratio
commission  = gross − thlNet
```

**Use the ratio, not a stored percentage** — `rrp/netRate` is convention-agnostic, so "25% on RRP" vs "33% on net" can't be misread into a wrong price. It reconciles by construction.

### Keeping the cached margins fresh — delta refresh, not per-search

**At search time**, the THL branch of the transportsoa fan-out makes **one `VehAvailRate` call for all brands** (one key covers all five AU/NZ brands; filter by `Vendor` client-side if needed), then applies the **cached** margin to each returned vehicle to produce `gross` + `commission`, and merges with the Jucy/RCM results before returning to TDMS. So the whole THL element is a single supplier call, same shape as the other branches — and the margin must be a **warm cache read, never a live call on the critical path**, which is the whole reason to pre-refresh it.

Don't look the margin up per search. **Cache every THL product's margin and PPDID** and refresh them on a timer with the product-delta endpoint:

```
GET /apiv1/products/lastUpdate?productIds=<THL set>&updatedAfter=<watermark>&sortBy=lastUpdated&sortDirection=desc
```

It returns only the products changed since the watermark — `{ productId, lastUpdated, active }`. For each changed id, refetch its prices, recompute the margin, and advance the watermark to the newest `lastUpdated` seen. Run it **hourly** (or on the sync cron).

Why this over a per-search lookup: the guest search then does **zero** price calls, and CMS load is one predictable hourly batch instead of search-driven traffic. The per-search lookup is otherwise **sequential** — you only know which `productId`s to price *after* `VehAvailRate` returns the Codes, so it can't overlap the availability call; pre-warming removes that round-trip from the critical path. Staleness is bounded by the interval and is **cosmetic** (sell price only — settlement always uses THL's real net), so an hour or two is fine.

Implementation notes:

- **Which API + creds** — both the `price` and `lastUpdate` calls are on the **Agent / Reseller API** (the same API agents use — see its section in these docs), not THL. Its credentials are **already in the account Secrets Store**; read them via a binding (`await env.X.get()`, the same pattern as `BREVO_API_KEY`) — no new credential to provision, just add the binding. So the pricing side is a small REST/JSON client to an internal WebsiteTravel API.
- **The `productId` set + `Code`→`productId` mapping come from `worker-wt-product-sync`.** Its D1 registry (the 66-vehicle Appendix-A catalogue + `product_links`) is the authoritative list of which THL products exist and their CMS `productId`s. transportsoa's margin-refresh reads that set (the linked/live rows) to drive the `lastUpdate` poll, and reuses the same `Code`→`productId` mapping to join a `VehAvailRate` result to its CMS product at search time. Consume it via a read-only D1 binding or a small endpoint — implementation TBD.
- **URL-encode the `+`** in `updatedAfter` as `%2B` — a literal `+` in a query string decodes to a space (e.g. `2026-02-13T00:00:00%2B0000`). Same gotcha the Worker already handles for TDMS dates.
- **Watermark from the data, not the clock** — advance it to the max `lastUpdated` processed, not local "now", to avoid skew and missed records.
- **Honour `active`** — a product flipping inactive should drop out of the sell set.
- **Page** with `recordStart`/`recordLength` (compare `fetchedRecords` vs `totalRecords`) for the rare bulk update.
- **Coerce `totalRecords`** — declared `String`, returned as a number.
- **Where the margin lives — and where it doesn't.** The margin's *source* is a **manual CMS fare** — on a live product the fare is a **margin carrier, not a price** (e.g. the live Spaceships fare is RRP 1.00 / Net 0.78 = 22%, plus an agent-pricing-group row), set by a person at product config. `worker-wt-product-sync` (the content sync) **deliberately does not touch `/price`** — it is content-only. So the margin **read + cache + refresh is `worker-transportsoa`'s job** — it's the consumer that needs gross. Cache the margin (+ `ppdid`) in **transportsoa's own store**: **KV** suffices for a pure search read-cache, **D1** if the Sync UI will also query it to display. The Sync UI reads it to display and may **write it only when blank** (a manual fill for an empty entry) — it does not otherwise own or overwrite it.
- **No "product without a margin" state — gated upstream.** Support **cannot push a product live without an actual fare**, and a product that isn't live **isn't shown in search and isn't returned by `lastUpdate`** — so it never enters the cache. The cache therefore only ever holds live, fared products: the missing-margin case is gated out at the source, not just at product creation, and the Sync UI's write-if-blank covers any rare timing gap. The lazy `/product/{id}/price` fetch on a cache miss is unnecessary — keep it only as defensive belt-and-braces if at all.

Send that `gross` + `commission`, and **record `thlNet` as the operator cost**. Because the net is carried through directly (not re-derived from gross), what we owe the operator is always THL's real net — a margin discrepancy can only ever move the sell price, never the settlement. By convention the CMS margin equals THL's margin, so the sell price is right too.

Watch-outs: use only `status = "Live"` fares (discard `History` and `Draft` — a real response is mostly History); match `currency` to THL's; **guard a zero/absent `netRate`** (undefined ratio → flag, never divide); it's a **ratio** so the margin % stays constant as the live net moves (a flat `rrp − netRate` add-on would not); the lookup can be **cached per `productId`** (prices change rarely); and it depends on the **THL `Code` → `productId` mapping** (reference-data work a THL build needs anyway).

### Pricing tiers — a second net via `agentPricingGroupId` (future, not current build)

Everything above assumes **one** THL key, and so **one** net per product. THL may later issue a **second key that returns a *lower* net for the same vehicle** — the guest RRP is unchanged, we simply earn a larger margin on the bigger spread. This is the same shape as RCM's `_preferred` connections (same vehicle, same sell price, different net/commission), and it is **not a concern today** — but the data model should leave room for it.

**The selector is a second dimension, not a second channel.** RCM carries the tier *inside the channel name* (`RCM_SpaceShips_AU` vs `…_preferred`), which doubles the channel list per tier. THL instead carries it on the CMS fare: the fare is **`FareType = General`** with an **`agentPricingGroupId`** whose value is **assigned per Supplier Account (per brand)**. So `source` keeps naming only the brand (`THL_Maui_AU`), and `agentPricingGroupId` independently names the pricing group — two keys × N brands stays N channels, not 2N. (This is the "agent-pricing-group row" already visible on a live CMS fare, above.)

<Note>
The `/prices` **shape supports pricing groups** — `agentPricingGroupId` can carry a real id or be `null`. **Our build consumes the `null` (default) group**: one `THL_API_KEY`, one net per vehicle. A *non-null* group (a second THL key at a lower net) is the extension this subsection describes — the wiring below (`thlCredentials`, the storage dimension) is what isn't built, not the data shape. Whether THL's own products use non-null groups is a CMS-config/commercial question, not assumed here.
</Note>

**Resolution — key on the pair `(source, agentPricingGroupId)`:**

| `agentPricingGroupId` | THL key | CMS fare (margin) |
|---|---|---|
| `null` (default) | `THL_API_KEY` | the product's default fare |
| `<brand's group value>` | the tier key (e.g. `THL_API_KEY_PREFERRED`) | that group's fare row |

- **The pair, not the id alone, is the lookup key.** The id's value is *per Supplier Account*, so composing on `(source, agentPricingGroupId)` stops a group id from ever selecting a tier under the wrong brand.
- THL stays **one key per *tier*, not per brand** — the tier key still covers all brands; what varies per brand is the group-id *value*.
- **`thlCredentials` must become group-aware.** Today it ignores the channel and returns the single `THL_API_KEY`; a tiered build maps `(source, agentPricingGroupId) → tier key`. That map lives **server-side in the admin portal**, next to the secrets, with the `null`/default row always resolving to the base key.

**Storage — the margin cache gains a group dimension.** Today the product mapping stores one **`productId`** per `(source, Code)` — the single value TDMS needs (the "boilerplate" value). A tiered build also records the **`agentPricingGroupId` per brand**, keyed to `source` (the two can share the same name), and the cached **margin + PPDID then key on `(productId, agentPricingGroupId)`** rather than `productId` alone — because each pricing group has its **own CMS fare row**, hence its own `rrp/netRate` ratio.

**Why the RRP stays constant.** The ratio model above is unchanged *per group* — the group simply selects which fare's ratio applies to which key's net. Each group's fare is configured to the **same guest RRP**, so the lower-net group carries a larger implied margin and `net × ratio` still lands on that RRP. Settlement records THL's **actual net for the key that signed the call**, so the books stay exact per tier. ⚠️ Keeping the per-group RRPs aligned is then a **CMS configuration discipline**; if guaranteeing an identical RRP *structurally* matters more than preserving per-group ratios, anchor on the stored RRP directly (`gross = rrp`, `commission = rrp − net`) instead of the ratio. Decide that with THL's real second-key behaviour in hand.

**Shape illustration** (generic, not THL data): a fare at RRP `625.00` can appear as `agentPricingGroupId: null` → net `468.75` (**25%** margin) and `agentPricingGroupId: 6471` → net `406.25` (**35%**) — same fare, same RRP, lower net on the group. That's the tier shape the endpoint already supports; whether THL populates it is separate.

## Currency

Every money field carries a `CurrencyCode`, set by the **rental's country** — there is no "price me in X" lever.

| Country | Currency |
|---|---|
| Australia | `AUD` |
| New Zealand | `NZD` |

(The US/CA brands use `USD` / `CAD`, out of scope here.) For the AU/NZ build the currency is effectively a **region key** — `AUD` → the AU side, `NZD` → the NZ side; confirm the CMS has matching regions, and there's no FX. Amounts may carry a `DecimalPlaces` attribute (e.g. `2`) — **parse by the places sent**, don't assume a scale, or you misprice by 100×. The US samples show mixed currencies in one rental; not a concern for AU/NZ, but don't assume one currency per response.

## Locations &amp; office hours

THL has **no "list locations / hours" call**. Location data comes from two places:

- **The static list** — Appendix B (Motek branch codes + brands).
- **Embedded in responses** — a `VehAvailRate` location carries an `InformationURL` (the brand's branch page), and a `VehRetRes` reservation carries the depot `Address` and `OperationSchedules` (the office/operation hours). So address and hours *are* available, but only attached to a search or a retrieved booking, not as a reference feed.

## Product content is out-of-band

The `VehAvailRate` responses return, per vehicle: **code** (`VehMakeModel Code`, e.g. `2BTSM`), a **name** (`VehMakeModel Name`, e.g. `Ultima - 2 Berth` — sometimes a little richer, e.g. `Voyager - 4 berth motorhome with rear island bed`), **brand**, **berth / category** (`VehClass Size` / `VehType VehicleCategory`), and **pricing** (`VehicleCharge`). There is a **`PictureURL` field, but it is empty in every sample** — so no image is actually delivered.

What you do **not** get: images, marketing descriptions, specifications, feature lists, galleries or floor plans — the rich content Jucy serves. The API gives enough to **identify and price** a vehicle, not to **merchandise** it. So, like RCM, THL is effectively **IDs-only for content**: images/descriptions would be sourced by us or TDMS, keyed on the vehicle `Code`; TransportSOA passes IDs. Appendix A is likewise just `Name → Code → Brand`. There is no Jucy-style product-content endpoint to import from.
