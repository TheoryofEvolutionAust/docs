THL (Tourism Holdings Ltd) rents campervans and motorhomes across five AU/NZ brands — **Maui, Britz, Mighty, Apollo, MightyLITE** — plus separate US and Canada brands. Its agent/reseller integration is **"Aurora OTA"**: an [OpenTravel (OTA)](https://opentravel.org) vehicle-rental message set delivered over **SOAP**.

<Note>
**This section is scoping, not yet confirmed live.** Everything here is sourced from THL's *OTA Technical Documentation* (13 Aug 2026) and its appendices, **before** we have called the API. Mark each finding **confirmed live** (and roughly when) once a real staging call proves it; until then treat it as "documented, unverified". Codes and product IDs are examples — look yours up again.
</Note>

## How it differs from our other transport suppliers

This matters because it sets the build cost. Neither thing below exists in the TransportSOA Worker today.

| | THL Aurora OTA | Jucy | RCM |
|---|---|---|---|
| Transport | **SOAP 1.1 / 1.2 (XML)** | REST / JSON | REST / JSON |
| Auth | **Static API key header (`x-api-key`)** | static API key | HMAC signature per call |
| Product content | **IDs only** (content is a static list) | rich content via API | IDs only |
| Rate | **Net** (we add margin) | — | — |

So the real work in a THL build is just a **SOAP/XML client** — the booking flow itself maps cleanly onto our contract (see [Booking flow](/api-reference/thl/booking-flow)), and as of Nov 2026 auth is a static header, not a session. An earlier revision used a `LoginOK` session with a JWT replayed as `EchoToken`; THL has since **replaced that with the `x-api-key` header** (Guide D), removing the token-cache / re-login work entirely. The SOAP transport is the only net-new cost left.

The underlying rental platform is **"Motek"** — branch/location codes in requests are Motek codes (see Appendix B). The B2B admin that issues the API key is **Motek B2B** (`https://b2bmotek.thlonline.com`; older portal `https://motek.b2b.thlonline.com`).

## Authentication — a static API key header

THL **replaced the login/token session** with a static API key (Guide D, Nov 2026). Current model:

1. A B2B admin generates an API key in **Motek B2B** (Settings → Accounts → API Key → *Generate*). It is shown once then hidden; lost keys are regenerated, and a key can be revoked.
2. Send it as the **`x-api-key`** request header on **every** OTA call. No login call, no token in the payload.
3. Keys stay valid **until revoked or replaced** — no expiry, no refresh.

Implications for a Worker build (all simpler than the old session):
- **No token cache, no re-login, no `LoginOK` call.** Auth is now as simple as Jucy's static key — just a header.
- The old `EchoToken` in the request body is **gone** — remove it from every payload.
- Keep the API key in **Worker secrets** (Secrets Store), never in a repo or these docs.

<Note>
The earlier session model (`LoginOK` → JWT → `EchoToken`) is **deprecated**. The "NEW API Technical Documentation" still contains stale per-call cURL examples using the old `otautils` host and an EchoToken — ignore those; Guide D and the sample cURL are the current word on auth.
</Note>

## Common request parameters

Auth is the `x-api-key` **header** (above). The rest ride in the SOAP body:

| Parameter | Meaning |
|---|---|
| `Target` | `Production` for live, `Test` for test. Advisory only — identifies request origin. |
| `Version` | Message version (e.g. `1`). |
| `MaxResponses` | Cap on results returned (e.g. `3`). |
| `TimeStamp` | When the request was sent. |
| `POS` / `Source` | Point of sale: `RequestorID` `Type` = `22` (default), `ID` = agent code. |
| `ISOCountry` | e.g. `AU`. If omitted, OTA returns defaults (VehAvailRate defaults to `GP`). Passing it null/empty throws an error. |

**Headers:** `UserAgent`, `Content-Type` (`text/xml`) and **`x-api-key`** are mandatory; `SOAPAction` is optional (but SOAP 1.1 typically wants it, e.g. `http://www.thlrentals.com/Aurora/OTA/VehAvailRate`).

## Brands

One login covers all five AU/NZ brands. Each availability result carries the vehicle's brand, and you can filter (see [Booking flow](/api-reference/thl/booking-flow)).

| Brand | Code |
|---|---|
| Maui | `M` |
| Britz | `B` |
| Mighty | `Y` |
| Apollo | `A` |
| MightyLITE | `L` |

US (`Road Bear RV` `R`, `El Monte RV` `E`, `Mighty` `Y`) and Canada (`CanaDream` `D`) are separate region lists.

<Note>
The `Vendor` list in a `VehAvailRate` response is **broader than these five** — the AU samples also carry Apollo-group brands like **Hippie Camper** (`H`) and **Cheapa**. Map by the `Vendor Code` the response gives, don't hardcode the five.
</Note>

Note also that THL's only "category" dimension on a vehicle is the **berth bucket** `VehType VehicleCategory` (`V2`–`V6`) — there is no named Campervan/Car/Motorhome type in the response; brand is the real axis.

## Rates — net by default, gross (RRP) on request

THL's AU/NZ brands are **net rate** by default — *"All ATL brands are net rate"* — so TransportSOA applies the margin, consistent with the WebsiteTravel model. The rate type is a **mandatory `Status`** request parameter, and you get **one or the other per call**, never both at once:

| `Status` | Vehicle rate returned |
|---|---|
| `Available` | **Net** (what we mark up) |
| `Gross` | **Gross** — the RRP |

The response's `RateCategory` confirms which came back (`1` = Gross, `0` = Net). To show both net *and* RRP you'd make two calls, or take net and add the margin.

**Extras and insurance are different** — `GetExtraHireItems` returns **both** `GrossAmt` and `NettAmt` on every product, side by side (in THL's samples they're equal, but the fields carry both).

<Note>
This is a different pricing model from our other two suppliers. **Jucy and RCM are a commission model** — they return a gross/retail rate **plus an `agentCommission`**, and net is derived (gross − commission). **THL returns net directly** and has no commission concept; gross is just the alternate `Status`.
</Note>

### Feeding TDMS, which expects gross

TDMS expects TransportSOA to send a **gross** sell price (with commission), exactly as Jucy and RCM already do. THL gives us net and **no bridge** to gross — one response never yields the other, and there is no commission field — so for THL we have to *produce* the gross. Two ways:

- **Default: apply a WebsiteTravel margin to net** (one `Status=Available` call). `gross = net + margin`, and the commission we report **is** that margin. This fits the existing "net rate, we add the margin" model — but the margin is a **new THL config input**, because Jucy's/RCM's commission is supplier-set and varies by key, whereas THL's is ours to define.
- **Alternative: honour THL's own RRP** (two calls — `Available` + `Gross`). Send THL's `Status=Gross` as the gross and set `commission = gross − net`. Only worth it if TDMS must show THL's published retail; costs a second call and reconciling two responses.

Either way TDMS receives gross + commission. The real difference from Jucy/RCM: **their commission is the operator's** (per-key), **THL's is ours to define** — so a THL build needs a margin rule that the other two suppliers never required.

**The commission is a % of RRP, set by the operator** — that's the WebsiteTravel model for every supplier: the agent earns that %, and `net-to-operator = RRP − commission`. Jucy/RCM hand us that commission in the response; THL doesn't, so we reconstruct the % from CMS (next).

**Settlement stays correct even if a margin ever disagreed.** We **record THL's actual net as what we owe the operator**, carried straight through — not back-computed from gross. So if a stored margin ever differed from THL's real commercial margin, the operator is still paid their exact net (no accounting headache); a mismatch could only change the *displayed sell price*, never the settlement. By convention the CMS margin equals THL's margin anyway, so single-sourcing it from CMS (next) keeps the sell price right too.

### Proposed approach — read the margin from CMS's product prices

Rather than a new TransportSOA margin config (the thing that would drift), read the margin from **CMS's existing stored prices** for the mapped product, so CMS stays the single source:

```
GET /{supplierapi}/product/{productId}/prices
```

```json
{
  "results": [
    { "productPricesDetailsId": 7001, "fareName": "Adult", "status": "Live",  "currency": "AUD", "rrp": 199, "netRate": 150 },
    { "productPricesDetailsId": 7002, "fareName": "Child", "status": "Draft", "currency": "AUD", "rrp": 99,  "netRate": 70 }
  ]
}
```

The stored amounts are **indicative — what matters is the margin they imply** (e.g. `rrp 100 / net 75` → a **25% margin**). Take the **`Live`** fare in THL's currency and apply that margin to **THL's live net** using the ratio:

```
ratio       = rrp / netRate          # 100/75 = 1.333  (25% margin on RRP == 33% markup on net)
gross       = thlNet × ratio
commission  = gross − thlNet
```

**Use the ratio, not a stored percentage** — `rrp/netRate` is convention-agnostic, so "25% on RRP" vs "33% on net" can't be misread into a wrong price. It reconciles by construction.

### Keeping the cached margins fresh — delta refresh, not per-search

Don't look the margin up per search. **Cache every THL product's margin** and refresh it on a timer with the product-delta endpoint:

```
GET /apiv1/products/lastUpdate?productIds=<THL set>&updatedAfter=<watermark>&sortBy=lastUpdated&sortDirection=desc
```

It returns only the products changed since the watermark — `{ productId, lastUpdated, active }`. For each changed id, refetch its prices, recompute the margin, and advance the watermark to the newest `lastUpdated` seen. Run it **hourly** (or on the sync cron).

Why this over a per-search lookup: the guest search then does **zero** price calls, and CMS load is one predictable hourly batch instead of search-driven traffic. The per-search lookup is otherwise **sequential** — you only know which `productId`s to price *after* `VehAvailRate` returns the Codes, so it can't overlap the availability call; pre-warming removes that round-trip from the critical path. Staleness is bounded by the interval and is **cosmetic** (sell price only — settlement always uses THL's real net), so an hour or two is fine.

Implementation notes (from the endpoint spec):

- **URL-encode the `+`** in `updatedAfter` as `%2B` — a literal `+` in a query string decodes to a space (e.g. `2026-02-13T00:00:00%2B0000`). Same gotcha the Worker already handles for TDMS dates.
- **Watermark from the data, not the clock** — advance it to the max `lastUpdated` processed, not local "now", to avoid skew and missed records.
- **Honour `active`** — a product flipping inactive should drop out of the sell set.
- **Page** with `recordStart`/`recordLength` (compare `fetchedRecords` vs `totalRecords`) for the rare bulk update.
- **Coerce `totalRecords`** — declared `String`, returned as a number.
- **Surfaced and set in the Sync UI** — the stored margin is shown per product and set/confirmed when a product is configured. A product is **not sellable without a fare** (its `rrp`/`netRate`), so a margin exists by construction the moment the product exists — there is no "product without a margin" state to handle. The UI can also refresh that product's margin on save, so a just-configured product is warm immediately.
- **Brand-new product edge mostly dissolves** — because the fare is mandatory at creation and that creation is itself an update the delta endpoint reports, a new product is picked up on the next poll (or on save). A lazy `/product/{id}/prices` fetch on a cache miss is then optional belt-and-braces, not a requirement.

Send that `gross` + `commission`, and **record `thlNet` as the operator cost**. Because the net is carried through directly (not re-derived from gross), what we owe the operator is always THL's real net — a margin discrepancy can only ever move the sell price, never the settlement. By convention the CMS margin equals THL's margin, so the sell price is right too.

Watch-outs: use only `status = "Live"` fares (ignore `Draft`); match `currency` to THL's; **guard a zero/absent `netRate`** (undefined ratio → flag, never divide); it's a **ratio** so the margin % stays constant as the live net moves (a flat `rrp − netRate` add-on would not); the lookup can be **cached per `productId`** (prices change rarely); and it depends on the **THL `Code` → `productId` mapping** (reference-data work a THL build needs anyway).

## Currency

Every money field carries a `CurrencyCode`, set by the **rental's country** — there is no "price me in X" lever.

| Country | Currency |
|---|---|
| Australia | `AUD` |
| New Zealand | `NZD` |

(The US/CA brands use `USD` / `CAD`, out of scope here.) For the AU/NZ build the currency is effectively a **region key** — `AUD` → the AU side, `NZD` → the NZ side; confirm the CMS has matching regions, and there's no FX. Amounts may carry a `DecimalPlaces` attribute (e.g. `2`) — **parse by the places sent**, don't assume a scale, or you misprice by 100×. The US samples show mixed currencies in one rental; not a concern for AU/NZ, but don't assume one currency per response.

## Locations &amp; office hours

THL has **no "list locations / hours" call**. Location data comes from two places:

- **The static list** — Appendix B (Motek branch codes + brands).
- **Embedded in responses** — a `VehAvailRate` location carries an `InformationURL` (the brand's branch page), and a `VehRetRes` reservation carries the depot `Address` and `OperationSchedules` (the office/operation hours). So address and hours *are* available, but only attached to a search or a retrieved booking, not as a reference feed.

## Product content is out-of-band

The `VehAvailRate` responses return, per vehicle: **code** (`VehMakeModel Code`, e.g. `2BTSM`), a **name** (`VehMakeModel Name`, e.g. `Ultima - 2 Berth` — sometimes a little richer, e.g. `Voyager - 4 berth motorhome with rear island bed`), **brand**, **berth / category** (`VehClass Size` / `VehType VehicleCategory`), and **pricing** (`VehicleCharge`). There is a **`PictureURL` field, but it is empty in every sample** — so no image is actually delivered.

What you do **not** get: images, marketing descriptions, specifications, feature lists, galleries or floor plans — the rich content Jucy serves. The API gives enough to **identify and price** a vehicle, not to **merchandise** it. So, like RCM, THL is effectively **IDs-only for content**: images/descriptions would be sourced by us or TDMS, keyed on the vehicle `Code`; TransportSOA passes IDs. Appendix A is likewise just `Name → Code → Brand`. There is no Jucy-style product-content endpoint to import from.
